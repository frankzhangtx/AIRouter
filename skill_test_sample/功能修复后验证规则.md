# 功能修复后验证规则

当在本工程中完成一个功能或修复一个问题后，是否需要编译或运行测试，主要按“改动风险”和“可验证性”判断，而不是固定每次跑全量验证。

## 基本原则

- 只要改动可能影响 Android 构建结果，就需要至少执行一次编译验证。
- 如果改动包含业务逻辑、状态判断、数据转换或可单测的 bug 修复，应优先运行相关单元测试。
- 如果改动只涉及文档、注释或不参与构建的说明文件，通常不需要编译或测试。
- 如果本应验证但受限于网络、依赖、沙箱、设备或模拟器环境，需要明确说明未能完成验证以及具体原因。

## 需要编译验证的情况

以下改动完成后，默认至少运行：

```bash
./gradlew assembleDebug
```

适用场景包括：

- Kotlin 源码改动。
- XML 布局、菜单、导航、主题、颜色、字符串等资源改动。
- `AndroidManifest.xml` 改动。
- Gradle 配置或依赖改动。
- ViewBinding 相关布局或代码改动。
- Activity、Fragment、Adapter、自定义 View 等 UI 入口改动。

`assembleDebug` 可以发现编译错误、资源引用错误、布局 XML 错误、ViewBinding 生成错误、Manifest 配置问题和导航配置问题。

## 需要运行单元测试的情况

以下情况应考虑运行：

```bash
./gradlew testDebugUnitTest
```

适用场景包括：

- 改动了业务逻辑、数据转换、状态判断或工具函数。
- 修复的问题可以用 JVM 单元测试复现。
- 项目中已有相关测试。
- 新增测试成本合理，且能覆盖本次行为变化。
- 改动影响面较大，单靠编译无法证明行为正确。

修 bug 时，如果能复现，优先先运行相关测试确认失败，再修复，最后运行同一验证确认通过。

## 需要运行 lint 的情况

以下情况可考虑运行：

```bash
./gradlew lint
```

适用场景包括：

- 改动资源、主题、Manifest、权限或 SDK/API 相关代码。
- 改动可能引入 Android 静态检查问题。
- 用户明确要求更严格的验证。

## 设备或模拟器测试

`connectedDebugAndroidTest` 不默认运行，因为它依赖真机或模拟器环境：

```bash
./gradlew connectedDebugAndroidTest
```

适用场景包括：

- UI 行为必须依赖设备验证。
- 已有相关 instrumented test。
- 用户明确要求运行设备测试。
- 本次改动涉及需要真实 Android 运行环境才能确认的问题。

## 编辑过程中的验证节奏

- 小改动：通常编辑完成后统一运行 `assembleDebug`。
- 大改动或跨多个文件：在一个稳定检查点先运行构建，避免错误堆积。
- 修复 bug：能复现时先确认失败，再修复，再用同一命令确认通过。
- 高风险改动：优先缩小验证范围，再逐步扩大到编译、单元测试或 lint。

## 不需要验证的常见情况

以下改动通常不需要运行编译或测试：

- 纯 Markdown 文档改动。
- 注释或说明文字调整，且不影响代码行为。
- 不参与 Android 构建的辅助文件改动。

即使不运行验证，也应在最终说明中明确“未运行测试/编译”的原因。
