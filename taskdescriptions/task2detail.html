Reading Guide

开始操作前先记住四条边界

这些边界决定任务是否真正通过质量门禁，而不只是“代码看起来能用”。

01
入口

先找 Planner

用户只输入业务描述。不要预先创建 TASK-ID、计划或 JSON 合同。

审批

C0 必须明确批准

初始需求不等于批准。只有用户明确回复批准后，Planner 才能生成合同。

审查边界

Reviewer 前不提交

Coder 产生的产品 diff 在 Reviewer 完成前不能提交或改变，否则 SHA 校验失败。

最终状态

只到 AWAITING_HUMAN

V1 不自动提交、push 或 merge，最终风险接受和合入决定始终由人负责。

任务输入：当前代码的城市列表没有“重庆”，因此“查看重庆的记录列表”虽然会命中列表意图， 但 slots.city 是 null。任务要求通过 TDD 增加该支持。
最终目标：查看重庆的记录列表 解析成功， userGoal == BrowsePersonalInfoList，并且 slots.city == "重庆"。

Manual Steps

按顺序执行的十一项操作

所有尖括号占位符都必须替换成 Planner 或终端实际生成的值。

先做发现检查和影子预检。此阶段不排队，也不修改产品代码。

启动交互式 Planner

不要自己指定 TASK-ID，也不要预先创建 Markdown 或 JSON 合同。

opencode --agent scheduled-planner .

进入 OpenCode 后粘贴：

当前代码的城市列表没有“重庆”，因此“查看重庆的记录列表”虽然会命中列表意图，
但 slots.city 是 null。任务要求通过 TDD 增加该支持。

审核 Planner 的 C0 提案并明确批准

提案应当只覆盖一个可观察行为，并明确以下范围：

  • 输入为 查看重庆的记录列表。
  • userGoal == BrowsePersonalInfoList。
  • slots.city == "重庆"。
  • 先写失败测试，再做最小实现。
  • 上海等已有城市行为保持不变。
  • 不增加区县、别名或模糊匹配。
  • 不改 UI、导航、依赖、Gradle、远端解析或意图优先级。
  • deviceTestsRequired == false。

确认无误后，在 OpenCode 中回复：

批准这个方案，生成计划和任务合同。
批准后才应该生成 docs/plans/<TASK-ID>.md 和 automation/tasks/<TASK-ID>.json。如果提案范围不正确，应继续澄清，不能批准。

复核合同并提交规划基线

退出 Planner 或另开终端，再次使用确定性脚本验证合同。

./scripts/automation/validate-contract.sh <TASK-ID>
git status --short

git add docs/plans/<TASK-ID>.md
git add automation/tasks/<TASK-ID>.json
git commit -m "Add approved Chongqing city task"

git rev-parse HEAD
记录输出：git rev-parse HEAD 的结果就是后续使用的 <BASELINE-COMMIT>。只提交规划产物，不要夹带其他用户修改。

在仓库目录外创建专用 worktree

git worktree add /absolute/path/to/cctest-task \
  -b task/chongqing-city <BASELINE-COMMIT>

cd /absolute/path/to/cctest-task

人工编辑专用 worktree 中的 automation/config.json：

"enabled": true,
"mode": "active",
"dedicatedWorktree": "/absolute/path/to/cctest-task"
git add automation/config.json
git commit -m "Activate quality gate in dedicated worktree"
git status --short
通过标准：git status --short 没有输出。Coder 必须从已配置且干净的专用 worktree 启动。

人工批准并把合同排入队列

AUTOMATION_HUMAN_APPROVED=1 \
  ./scripts/automation/queue-task.sh <TASK-ID>

./scripts/automation/status.sh <TASK-ID> | jq -r '.state.state'
期望输出：PENDING。

手工启动 Coder

此命令手工运行未来 Scheduler 使用的同一个 Agent 和固定 Prompt。

opencode run --agent scheduled-coder -- \
  "$(<automation/scheduler/coder-prompt.txt)"
禁止添加 --dangerously-skip-permissions。Agent 的权限拒绝规则是质量门禁的一部分。

Coder 应自动完成：

  • G0：新增测试前，全量 testDebugUnitTest 必须通过。
  • G1：先添加重庆聚焦测试，获得真实 RED 并记录证据。
  • 最小实现：通常只需把“重庆”加入已知城市配置。
  • G2：聚焦测试与全量 JVM 单测通过。
  • G3：assembleDebug 通过。
  • G4：Android Lint 通过。
  • G5：依据合同跳过设备测试。
  • G6：修改范围、测试完整性和基线一致性通过。

检查 Coder 结果，但不要提交产品 diff

./scripts/automation/status.sh <TASK-ID> | jq -r '.state.state'
git diff --name-only HEAD --
git diff HEAD --

jq . automation/evidence/<TASK-ID>/red.json
jq . automation/evidence/<TASK-ID>/ready.json
期望状态：READY_FOR_REVIEW。确认 red.json 是实现前因重庆未识别而产生的真实失败， 并确认 ready.json 已保存 HEAD 和 diffSha256。
Reviewer 完成前不要提交、修改或格式化产品代码。任何 diff 变化都会破坏已封存的 SHA，导致 CHANGES_REQUESTED。

启动全新的只读 Reviewer

不要继续使用 Coder 会话；新进程会创建独立上下文并重新运行确定性验证。

opencode run --agent scheduled-reviewer -- \
  "$(<automation/scheduler/reviewer-prompt.txt)"

./scripts/automation/status.sh <TASK-ID> | jq -r '.state.state'
jq . automation/evidence/<TASK-ID>/review.json
通过必须同时满足：state == AWAITING_HUMAN、 decision == APPROVED、verificationExitCode == 0。

执行 H1 人工最终验收

检查完整状态、产品 diff 和三类关键证据。

./scripts/automation/status.sh <TASK-ID> | jq .
git status --short
git diff --name-only HEAD --
git diff HEAD --

jq . automation/evidence/<TASK-ID>/red.json
jq . automation/evidence/<TASK-ID>/ready.json
jq . automation/evidence/<TASK-ID>/review.json

如需人工再次执行完整确定性验收：

./scripts/automation/verify-task.sh <TASK-ID>

人工提交产品修改并选择性合入

只有 H1 全部通过后，才能提交合同允许的产品源码和测试。例如：

git add app/src/main/java/com/example/cctest/routing/parser/TextParsingSupport.kt
git add app/src/test/java/com/example/cctest/routing/RuleBasedIntentParserTest.kt
git commit -m "Add Chongqing city recognition"
如果要把成果带回主分支，只选择性合入这个产品提交。不要把含本机绝对 worktree 路径的自动化激活提交合入主分支。
H1 Acceptance

最终人工验收清单

业务、测试、范围和证据必须全部通过，缺少任意一项都不能视为完成。

04

业务行为

  • 查看重庆的记录列表 返回成功解析结果。
  • userGoal == BrowsePersonalInfoList。
  • slots.city == "重庆"。
  • 上海等已有城市行为保持不变。
  • 没有增加区县、别名或模糊匹配。

测试与构建

  • 存在实现前的真实 RED 证据。
  • 聚焦测试与全量 JVM 单测通过。
  • Debug APK 构建通过。
  • Android Lint 通过。
  • 合同明确设备测试不需要执行。

范围与权限

  • 产品 diff 只落在合同允许路径。
  • 没有修改 Agent、Skill、合同、门禁脚本、Gradle 或依赖。
  • 没有删除、忽略或弱化测试。
  • Coder 没有 push、merge、rebase 或创建 worktree。
  • Reviewer 是独立只读会话，未编辑仓库文件。

状态与证据

  • ready.json 记录 HEAD 与 diff SHA。
  • review.json.decision == "APPROVED"。
  • verificationExitCode == 0。
  • 最终状态为 AWAITING_HUMAN。
  • Reviewer 前产品 diff 没有被提交或改变。

Failure Handling

失败状态与重新排队

失败不是继续猜测的信号，而是停止、保留证据并交还人类处理的信号。

06
状态 常见原因 正确处理
BLOCKED 环境、合同、基线、worktree 或修改范围不满足硬门禁。 保留日志，修复环境或合同问题，不要自动重试。
TEST_FAILED 聚焦测试、全量单测、构建或 Lint 在允许修复次数后仍失败。 人工检查失败证据并修复代码，再重新批准排队。
CHANGES_REQUESTED Reviewer 发现语义、测试质量或 diff SHA 不一致。 根据 review.json 修复；Reviewer 不得自己编辑代码。

问题解决后，必须重新由人明确批准排队： 

AUTOMATION_HUMAN_APPROVED=1 \
  ./scripts/automation/queue-task.sh <TASK-ID>
不得在脏主工作区运行 Coder，不得跳过权限，不得在 Reviewer 之前提交产品 diff，也不得让 V1 自动 push 或 merge。
