先抓住零配置版本的四个重点

这是阅读抓手：先理解边界，再复制后面的命令。

1. Gradle 质量矩阵自动生成

临时只读 init script 发现实际注册任务；0.6.0 只为这次调用禁用配置缓存。普通任务折叠为通用选择器，flavor 任务保留精确路径。

2. 白名单是精确文件列表

.automation-worktree-allowlist 一行只写一个仓库相对文件路径，不接受目录、glob 或受保护路径。

3. 批准合同时固定快照

白名单在合同批准时写入任务 workspace。任务中途修改控制文件不会扩大当前任务权限，只影响下一次任务。

4. 本地改动不会混入提交

命中白名单的 tracked、untracked、staged 改动不进入范围、哈希、证据和提交；原有 staged 状态也会保留。

第 1 步（可选）：确认 0.6.0 版本存在

这是只读检查，可以跳过，不会改动 WordPress 工程文件。

命令输出 0.6.0 就表示该固定版本存在。它只查询 Registry， 不会安装插件；即使跳过本步，也可以直接执行第 2 步。第 2 步的固定版本 npx 会取得并运行该包，不需要先做全局安装。

第 2 步：自动发现并初始化

不传项目专用参数。开始前必须保证 WordPress 工作区干净。

# 进入 WordPress 工程
cd /Users/zhanglong/files/program/wordpresslocal/WordPress

# 确认当前没有未提交修改；有输出时先不要继续
git status --short

# 首次初始化执行一次；项目已忽略该目录时可跳过
echo ".automation-plugin/" >> .git/info/exclude

# 固定使用已发布的 0.6.0，自动识别模块、flavor 和 Gradle 验证任务
npx --yes @frankzhang2026/opencode-android-orchestrator@0.6.0 \
  init . \
  --json
不需要添加 --module-scope、--primary-module 或 --gradle-verification-config。根工程的 .apply(false) 不再被误判为 Android 模块，唯一应用模块会自动识别为 :WordPress。 旧的 WordPress 专用 Gradle 验证 JSON 已无用途，不应复制到 WordPress 工程或重新传给 CLI。 init 还会在根目录缺失时自动创建只含注释的 .automation-worktree-allowlist，已有普通文件则原样保留。 WordPress 的 gradle.properties 已启用 Configuration Cache；0.6.0 内部只对 临时 gradlew help 发现调用增加 --no-configuration-cache，不会修改 项目文件，正常构建继续使用原有缓存配置。 查询失败会在安装写入前以 GRADLE_DISCOVERY_FAILED 结束，不会使用漏测矩阵继续。 
# 仅在任务发现失败时复现同一配置阶段边界
./gradlew help --no-configuration-cache --console=plain
不要通过删除 Configuration Cache 或关闭 org.gradle.configuration-cache=true 长期绕过错误；应修复命令报告的 JDK、依赖解析或 Gradle 配置问题。

第 3 步：验证并提交安装结果

插件工作流要求源分支保持干净，因此安装生成的文件需要先提交。

# 验证安装
npx --yes @frankzhang2026/opencode-android-orchestrator@0.6.0 \
  doctor . --json

# 查看安装产生的文件
git status --short

# 确认只有本次安装文件后提交
git add --all
git commit -m "Install OpenCode Android Orchestrator"
doctor 的 JSON 中应看到 "ok": true。提交前先看一遍 git status --short；如果混入了原有业务修改，不要直接执行 git add --all。

可选：填写需要保留的本地文件

init 已自动创建白名单；只有确实需要长期保留本地改动时才需要编辑。

cd /Users/zhanglong/files/program/wordpresslocal/WordPress

# 文件已由 init 创建；仅在需要时由人编辑，Agent 不应修改
nano .automation-worktree-allowlist

白名单文件内容示例，空行和以 # 开头的行会被忽略：

# One exact repository-relative file path per line
local/operator-note.txt
docs/local-review-notes.md

保存后，用受管 preflight 验证列表与当前工作树：

./scripts/automation/preflight.sh --source
  • 必须写精确的仓库相对文件路径；不能写目录、*、?、重复项、../ 或符号链接控制文件。
  • automation/、scripts/automation/、Gradle、Git、计划与其他受保护路径不能加入白名单。
  • 某个任务需要修改该文件时，必须先结束当前任务、删除对应条目，再批准新任务。
  • 重命名同时包含旧路径删除和新路径新增；若两边都要留在本地，旧、新两个精确路径都要列出。
  • 普通 git status 仍可能显示控制文件和本地改动，但 Orchestrator 会使用审批快照过滤它们。
  • 该文件不进入受管资源哈希，所以填写条目不会让 doctor 报资源篡改；升级和卸载也会保留它。
白名单不是“允许 Agent 编辑”的授权，而是“让该本地文件完全退出本次自动任务”的排除项。 被排除的内容不会接受 Reviewer 检查，也不会进入验收证据或任务提交。

日常只需要记住这些命令

TASK-ID 会在运行任务后显示，例如 TASK-ARTICLE-REFRESH-001。

开始新需求

/change <一句话需求>

最常用的入口。一次只提交一个小型行为变化。

重新打开验收

/acceptance <TASK-ID>

错过验收页面或准备稍后验收时使用。

恢复 Reviewer

/resume-review <TASK-ID>

Reviewer 会话中断、任务明确停在复核阶段时使用。

安全中止

/abort-task <TASK-ID>

停止任务、封存已有修改并安全回到原分支。

核心源码摘录

注释仅用于帮助阅读，不会回写插件源码；摘录聚焦白名单的安全边界。

templates/scripts/automation/lib.sh · status.sh · accept-and-integrate.sh
# lib.sh：控制文件名固定，大小和条目数都有上限
AUTOMATION_WORKTREE_ALLOWLIST_RELATIVE_PATH=".automation-worktree-allowlist"
AUTOMATION_WORKTREE_ALLOWLIST_MAX_BYTES=65536
AUTOMATION_WORKTREE_ALLOWLIST_MAX_ENTRIES=256

# 只做完整字符串匹配；控制文件自身也从自动任务视图中排除
[[ "$path" == "$AUTOMATION_WORKTREE_ALLOWLIST_RELATIVE_PATH" ]] && return 0
while IFS= read -r entry; do
    [[ -n "$entry" ]] || continue
    [[ "$path" == "$entry" ]] && return 0
done <<< "$entries"

# 禁用 rename 折叠：新路径命中白名单时，旧路径删除仍然可见
paths="$(git -C "$root" diff --no-renames --name-only HEAD -- | LC_ALL=C sort -u)"

# status.sh：Coder / Reviewer 能看到任务真正生效的快照
effective_worktree_allowlist_json="$(
    automation_effective_worktree_allowlist_json_at "$task_root"
)"
runtime: { effectiveWorktreeAllowlist: $effectiveWorktreeAllowlist }

# accept-and-integrate.sh：只提交过滤后得到的明确路径集合
git -C "$task_root" commit --only \
  -m "Implement $title ($task_id)" -- "${commit_paths[@]}"
三个关键点是：精确匹配避免目录级放行，--no-renames 保留重命名的源路径， commit --only 避免把此前已暂存的白名单文件顺带提交。任务中止时的恢复提交也使用相同的明确路径策略。

白名单在一次任务中的执行流程

流程从人工维护控制文件开始，到任务提交后本地排除项继续保留为止。

菱形是安全判断或 workspace 分支，圆角矩形是处理步骤。左下角的“可见任务改动”最终通过 commit --only 形成任务提交；右下角的本地排除项始终留在任务提交之外。

首次安装和日常使用不需要执行下面的命令。

WordPress 已安装旧版本，如何升级到自动发现版本？
先用目标版本运行 doctor，再升级并复核已安装质量矩阵。升级默认保留旧安装的 矩阵，不会因为切换到 0.6.0 自动重新发现： 
npx --yes @frankzhang2026/opencode-android-orchestrator@0.6.0 \
  doctor . --json

npx --yes @frankzhang2026/opencode-android-orchestrator@0.6.0 \
  upgrade . \
  --json
如果旧矩阵漏掉 flavor，应先在临时干净 checkout 中执行 0.6.0 首次 init 核对自动发现结果，再使用经审核的工程内覆盖文件，或安全卸载后 重新初始化。当前 WordPress 没有安装 manifest，应直接首次 init，不走升级。 如果从缺少 moduleScope 的 0.2.0 直接升级，默认会保留为 primary；只有明确要扩到全部模块时，才额外传入 --module-scope all。
如何确认某个任务实际使用了哪些白名单条目？
合同批准并生成 TASK-ID 后读取任务状态；查看的是审批快照，不是此刻控制文件的新内容： 
./scripts/automation/status.sh TASK-ARTICLE-REFRESH-001 \
  | jq '.runtime.effectiveWorktreeAllowlist'
原地任务返回已批准的精确路径数组；隔离工作树内返回 []，避免源工作树白名单隐藏任务工作树中的同名改动。
如何卸载？
在 WordPress 根目录运行： 
npx --yes @frankzhang2026/opencode-android-orchestrator@<已安装版本> \
  uninstall . --json
安装或运行失败怎么办？
  • 先运行固定版本的 doctor . --json，按失败项处理。
  • 确认从 WordPress Git 根目录运行，且 gradlew 可执行。
  • 任务发现失败时运行 ./gradlew help --no-configuration-cache --console=plain；不要关闭项目级 Configuration Cache 掩盖根因。
  • 确认 OpenCode 版本为认证过的 1.14.22 或 1.15.13。
  • 白名单校验失败时修正具体条目；不要把目录改成 glob，也不要放宽 protectedPaths 绕过错误。
  • 不要删除或手工修改 .automation-plugin/。
  • 任务执行中需要停止时，使用 /abort-task <TASK-ID>。
