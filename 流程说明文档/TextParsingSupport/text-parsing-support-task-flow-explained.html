Requirement Analysis

需求分析：从现有代码缺口出发

02
Existing behavior

旧逻辑只接受连续 11 位数字

原来的 extractPhone 使用 Regex("1\\d{10}")。 它能识别 13800001022，但遇到 138-0000-1022 或 138 0000 1022 时返回空， 导致表单解析结果缺少手机号槽位。

Observable goal

输入形式更宽容，输出形式仍唯一

新能力只扩展输入格式，不改变下游数据契约。无论用户输入连续、短横线分组还是空格分组， personalInfoFields.phone 都必须得到同一个纯数字值 13800001022。

输入示例 预期结果 原因
13800001022 13800001022 保持已有连续格式兼容性。
138-0000-1022 13800001022 接受 ASCII 短横线的 3-4-4 分组。
138 0000 1022 13800001022 接受 ASCII 空格的 3-4-4 分组。
138-000-1022 null 分组位数不完整，不能把近似文本误认为手机号。
138-0000-10222 null 总位数超长，必须被数字边界拒绝。
138a0000a1022 null 字母不是本任务允许的分隔符。
范围控制：本任务不修改 UI、导航、Gradle、依赖或远程解析；不处理国际号码，也不新增运营商号段校验。 这是一个输入抽取规则的原子变更，适合用本地 JVM 测试完成，不需要设备或模拟器。

// 三个分支只覆盖合同批准的格式：
// 1) 连续 11 位；2) 短横线 3-4-4；3) 空格 3-4-4。
private val mainlandMobilePhonePattern = Regex(
    "(?<![0-9])(?:1[0-9]{10}|" +
        "1[0-9]{2}-[0-9]{4}-[0-9]{4}|" +
        "1[0-9]{2} [0-9]{4} [0-9]{4})" +
        "(?![0-9])"
)

fun extractPhone(text: String): String? {
    // 未命中返回 null；命中后移除空格或短横线，只向下游交付数字。
    return mainlandMobilePhonePattern
        .find(text)
        ?.value
        ?.filter(Char::isDigit)
}

为便于阅读，代码在 HTML 中被换行并加入解释性注释；源码中的语义与这里一致，但注释没有回写到 Kotlin 文件。

Boundary

前后数字边界

(?<![0-9]) 和 (?![0-9]) 防止从更长数字串中截取一个“看起来合法”的 11 位子串。

Compatibility

保留旧输入

1[0-9]{10} 仍是第一个分支，原来的连续格式不受影响。

Normalization

输出只有一种形态

filter(Char::isDigit) 去掉空格或短横线，避免下游每个消费者重复处理格式差异。

正则分支 接受内容 为什么不做更宽泛匹配
1[0-9]{10} 连续 11 位、以 1 开头 保持旧行为。
1[0-9]{2}-[0-9]{4}-[0-9]{4} ASCII 短横线 3-4-4 不接受任意数量短横线，避免误识别。
1[0-9]{2} [0-9]{4} [0-9]{4} ASCII 空格 3-4-4 只实现合同明确批准的常见输入。

1 · 基线
先提交计划、合同和 harness 配置

建立干净、不可变的 Git HEAD；创建专用 worktree，并在配置中填入绝对路径。

2 · 激活
人工把 shadow 切换为 active 并排队

S0 与 G0 必须新鲜通过

scheduled-coder 获取锁并进入 CODING

5 · 门禁
quality-gate.sh 唯一有权推进 READY_FOR_REVIEW

它调用 scope 与 verify 脚本，限制最多一次修复，归档退出码，计算最终 diff SHA-256； 任一范围或证据门禁失败都进入 BLOCKED / TEST_FAILED。

scheduled-reviewer 只读复核

在独立会话重跑关键命令、检查测试强度与语义风险，只能给出 APPROVED 或 CHANGES_REQUESTED，不能改代码。

7 · 人工
H1 决定提交、合并、退回或放弃

定时自动化到 AWAITING_HUMAN 为止；V1 不自动 push，不自动 merge。
